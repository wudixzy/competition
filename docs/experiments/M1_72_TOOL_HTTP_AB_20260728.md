# M1-72 tool HTTP compatibility A/B

Date: 2026-07-28

## Motivation

The latest saved platform result completed 631 of 881 requests and reported
226 tool-request 4xx responses. Those aggregate counters do not identify a
single root cause, so they cannot justify estimating a success-rate gain.

M1-68 reproduced two concrete compatibility gaps in the frozen CoreX vLLM
0.6.3 request path:

1. an OpenAI function definition that explicitly carries `strict=false`;
2. assistant tool-call history whose JSON arguments are already represented
   as an object.

The M1-68 component and tokenizer gates passed, but they did not start a real
API service or execute model weights. M1-72 closes only that evidence gap.

## Frozen comparison

The two immutable overlays are:

| Arm | Revision | Expected behavior |
| --- | --- | --- |
| baseline | `c78d55d0a7637baf4910af68b6d6ba4e286a1254` | both equivalent forms return HTTP 400 |
| candidate | `cdb1bc41f728a5610a3632ad7923d73a90748919` | both equivalent forms return HTTP 200 |

The runtime verifier requires exact install reports and an exact three-file
delta: `api_server`, `chat_utils`, and `protocol`. Any other installed-file
delta or overlay mutation invalidates the run.

Both arms use the same four-layer real-weight Qwen3.6 diagnostic checkpoint,
physical GPU, seed, request order, model arguments, and disabled rejected
compute candidates. They retain `max_model_len=262144`, `temperature=0`,
`thinking=false`, and the original tokenizer and chat template.

## HTTP contract

Each arm executes nine synthetic, privacy-safe cases:

1. `/v1/models` advertises 262144 tokens;
2. a default function tool succeeds;
3. `strict=false` reproduces baseline HTTP 400 and candidate HTTP 200;
4. JSON-string tool-call history succeeds;
5. object tool-call history reproduces baseline HTTP 400 and candidate
   HTTP 200;
6. malformed JSON tool arguments remain HTTP 400;
7. unsupported `strict=true` remains HTTP 400;
8. unsupported `tool_choice=required` remains HTTP 400;
9. the service remains healthy after expected 4xx responses.

The candidate's accepted equivalent forms must generate exactly the same
message, finish reason, prompt-token count, and completion-token count as
their canonical forms. Canonical requests must also remain exact across the
two overlays.

Candidate 4xx access records must reconcile one-for-one with exactly these
privacy-safe reason codes:

- `invalid_tool_arguments_json`;
- `request_validation_tool_strict`;
- `unsupported_tool_choice_required`.

The current v3 reconciler accepts the frozen candidate's older v2 shape
markers without inventing unavailable shape fields. It still fails closed on
missing, malformed, unknown, or unclassified markers.

## Resource and cleanup contract

The two arms use distinct preflighted ports. Each service starts in a new
process group. Cleanup sends SIGTERM only to that group, waits 60 seconds,
uses SIGKILL only for survivors, and waits/reaps the leader.

Every arm and the outer runner require:

- a clean service/worker/GPU postflight;
- a repeated per-card compute preflight;
- bounded free-memory comparison;
- empty fatal, Gloo, NCCL, worker-loss, and timeout scans.

A failed postflight invalidates the experiment even if the HTTP probe passed.
