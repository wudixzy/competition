# M1-161 tail64 TTFT P90 trace diagnostic

## Purpose

The platform result for `503fa7c670` reported global TTFT P90 of 27.49s.
Its successful-request buckets show that the global percentile lies around
the upper 16K-32K or lower 32K-64K population, so a cache policy must improve
first-use session branches rather than only repeated warm requests.

`tail64` is an experimental alternative to `admission64`. It retains the
canonical final prefill state and, when no observed repeated branch has
priority, one checkpoint at the last 8192-token boundary before prompt end.
It keeps the same 64-state capacity and the existing limit of two capture
actions per request. It does not change request semantics, model math, the
default policy, `computility-run.yaml`, or `main`.

## Simulator repairs

The trace simulator now mirrors runtime `hybrid64` eligibility, including the
non-64-aligned exact final-state exception. Before this repair, a real exact
warm hit was incorrectly modeled as a miss and produced invalid TTFT scaling.

The diagnostic mode `--tail64-pair-only` executes only `admission64` and
`tail64`. Its report cannot authorize promotion. The KV eviction replay now
uses a lazy validated heap with the exact previous ordering key. On the
four-request trace, the heap and prior scan produced byte-identical reports.
The 31-request comparison dropped from more than 189 seconds without
completion to about one second on the same host.

## Directional results

The source traces are privacy-safe M1-125 cache trace v4 logs produced at
runtime source `e59ebb6`. Analysis used `4e76b2b` with `hybrid64`, block size
16, chunk size 8192, and no CPU KV tier.

| Trace | Requests | Improved / unchanged / regressed | Effective-hit gain | Projected TTFT P90 |
| --- | ---: | ---: | ---: | ---: |
| 32K A/A/B/B | 4 | 1 / 3 / 0 | +18.75 pp | 38.05s to 28.04s (-26.3%) |
| Full quality trace | 31 | 2 / 29 / 0 | +7.08 pp | 372.50s to 370.80s (-0.46%) |

For the 32K sequence, `admission64` exactly reproduces the observed
cold/exact-warm/first-sibling-miss/subsequent-sibling-hit sequence. `tail64`
changes only the first sibling, reducing its residual prefill from 32768 to
8192 tokens. The projection scales that request's measured non-queue cold
prefill time and does not model the extra checkpoint capture cost.

The full quality trace is not workload-distribution evidence. It contains
only seven 32K-64K requests and its P90 is dominated by cold 235K and
near-262K cases. `tail64` improves one 32K-64K request and one 128K-256K
request, with no simulated regressions, but does not move the 32K-64K bucket
P90 in that small matrix.

## Decision

Retain `tail64` as an experimental cache candidate and combine it with a
cold-prefill optimization when TP4 is healthy. Do not promote it as the TTFT
P90 solution by itself. A service A/B must measure checkpoint overhead,
cold/warm output transparency, per-request cached-token accounting, and the
16K-64K P90 before any default change. The current evidence is offline and
does not authorize `main`, YAML, or official-score claims.
